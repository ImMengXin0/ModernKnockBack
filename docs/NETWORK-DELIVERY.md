# 网络延迟缓解补丁（2.4.0）

本补丁减少服务端批量发送产生的额外等待，在 classic / modern 下自动生效，不添加任何 config 项。它是发送时机优化，不是位置回溯、补打或按 Ping 修改击退。

## 行为

- 玩家本人的速度包写入现有 Netty 通道后，立即调用 flush，避免继续等待核心的批量刷新。近战、鱼竿和其他来源的本人速度使用相同处理。
- 爆炸包可能携带接收者专属击退，也及时刷新，包括仅含爆炸效果的包。其他实体的速度与普通包继续正常批量处理。
- 包在现有处理链中正常传递，不创建额外速度包，不改变向量，不直接绕过 KnockbackSync 或核心的写入处理。flush 只把已经写入的内容往下游提交；前面的包仍在前面。
- 组合包整体写入后才刷新，不拆包，不在组合包中间插入一次击退或刷新。
- 核心已及时刷新时，通常没有额外收益；本补丁不承诺减少固定毫秒数。单次写入后多一次 flush 不会再次写入同一个速度包。
- 插件全局 `enabled: false`、排除玩家或卸载后恢复核心刷新行为；模式切换两边均保持此优化。profile 自身的 `enabled` 控制数值修改，不单独关闭连接发送优化。
- 重生更新本人实体 ID；所有通道操作属于该连接的事件循环，不从网络线程访问玩家或世界，因此不增加 Folia 跨区域访问。
- 包识别所需反射在启动时预热，延续首次击退初始化修复。

## 丢包与补偿边界

Java 版 Minecraft 使用 TCP。丢失的传输数据由 TCP 检测、重传并按序交付，应用层通常表现为延迟或一段时间后集中收到数据。插件无法从普通 Bukkit Ping 可靠得到丢包率，也无法让丢失的网络数据提前到达。

因此没有使用超时重发 KB、断网恢复补推或预测收到确认的办法。速度包不是一个可以任意重复的伤害通知：重发可能让已经衰减的速度重新生效，形成叠 KB。发生拥堵时保留 Netty/TCP 的正常背压、顺序和连接处理；补丁没有自己的包队列、重试任务或待补推状态。

不会延长受击窗口、扩大攻击距离、根据 Ping 加力或减力、扩大 jump reset 窗口，也不会把网络集中到达的旧攻击重新排队执行。原来的 CPS 密度计算与上限保持不变。这些属于战斗判定规则，而非传输层丢包恢复。

KnockbackSync 已接收和排队的内容仍由它自己处理；本补丁只能刷新已经到达 MKB 所在通道位置的写入，不能强迫上游插件释放尚未交出的包。顺序不变，但实际共存手感仍需联机验证。

## 验证

`VelocityPacketFlushTest` 用 Netty EmbeddedChannel 的未刷新写入检查两种模式及时提交、其他实体正常批量发送、组合包完整性、关闭/排除、重生 ID、不可写状态下不重放、过滤后的 promise、爆炸和写入失败不重试。不可写通道测试是背压逻辑测试，不是 TCP 丢包模拟。

`ServerBridgeProbe` 在 Leaf、ASPaper、Folia 的真实 1.21.11 运行库中检查包格式及组合包，验证未手动 flush 的本人速度能够交付且只交付一次，保留旧版受击效果过滤；关闭和移除恢复原行为。

实服应在正常重启替换 Jar 后，用相同玩家和 KB 配置对比普通网络、高 RTT、网络抖动及丢包重传期间的表现，确认竿接刀和连续近战没有额外补推。离线检查不代表已消除真实网络延迟或完成真实 KnockbackSync 共存测试。
